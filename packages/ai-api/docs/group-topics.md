# Group topics

An opt-in job in the stream worker summarises each group's finished conversations into `{subject, summary}` topics. In a group, `search_conversation_history` returns the matching topics first, then the matching messages. Idea and wa_llm bugs to avoid: the `wa-llm-research` peer report (Devflow `6af1dcc1be4cc60a82acc1b6`).

## Switch and cost

- `GROUP_TOPICS_ENABLED` (default `false`, hot via `PATCH /admin/settings` as `group_topics_enabled`). Both the worker loop and the search tool read it through `runtime_config.get()`, so turning it off also stops topic search, and a run in progress stops before its next block. While it is off, the loop re-reads it every 30 s, so turning it on starts a run within about 40 s (30 s poll plus the ~10 s settings cache).
- `GROUP_TOPICS_INTERVAL_MINUTES` (default `60`, min `5`, read once at worker start): time between runs.
- **Privacy**: off by default because it sends every group message, mentioned or not, to the chat model, and to DeepSeek (China) when `DEEPSEEK_API_KEY` is set. Without it, a non-mentioned message reaches a chat model only as one of the last `HISTORY_LIMIT_GROUP` history lines when someone mentions the bot. (Every group message already goes to Google's embedding API either way.)
- **Cost**: one model call per finished block, no tool schemas. A typical active group (100-300 messages a day in 2-5 conversations) costs about 3-6 calls a day, each about 2-6k input and ~300 output tokens: around US$ 0.01 per group per day on `gemini-3.1-flash-lite`, less on `deepseek-flash`. One embedding per topic. A group with nothing new costs one indexed query per run. A run reads at most the last 7 days, also after the job was off for longer (the messages between the old cursor and that window are never summarised, so a backlog written while it was off is never sent to the model), and each run summarises at most 10 blocks per group.

## How a run works

`streams/group_topics.py` `run_group_topics_loop` → `run_group_topics_once` → `rag/group_topics.py` `ingest_group` per group.

1. **Lease** (`streams/lease.py`): `SET group_topics:lock NX EX 600`, renewed before every block and released by token at the end, so one worker process runs at a time and a run that loses the lease stops before its next block. `group_topics_enabled` is re-read at the same point. A run stops starting new groups after 15 minutes; groups that waited longest go first.
2. **Groups**: `users.conversation_type = 'group'` rows with messages after their cursor and within the last 7 days (`groups_with_new_messages`, the same rules as the read), least recently ingested first. Groups whose last try hit a provider failure (Redis set `group_topics:deferred`) go last.
3. **Read**: messages after the cursor and within the last 7 days (without the `embedding` column), ordered by `(timestamp, id)` with a row comparison (ties can't skip or repeat), plus the 5 messages before them as context.
4. **Split** (`split_into_blocks`, pure): a pause over 2 h ends a conversation; one over 200 messages is cut into 200-message pieces; a piece under 25 is merged into the next. No block whose last message is under 2 h old is taken, so a chat still going is held back, its full 200-message pieces included; a conversation that runs for hours without a pause gets its older pieces summarised once they are 2 h old. A finished piece under 25 waits for the next conversation until it is 24 h old. Everything taken is at least 2 h old, so a message committed late (timestamps are insert-time) can't land behind the cursor. Each block carries the 5 messages before it, marked as context only.
5. **Summarise** (`summarise_block`): a narrow `Agent(output_type=list[Topic])` with no tools, on `build_runtime_model()` (DeepSeek → Gemini, honouring `/admin` model overrides and the DeepSeek cooldown). It runs through `run_stream_events`, not `run`: the model requests are then streamed, so `GuardedModel`'s first-chunk timeout applies and a DeepSeek request stuck in its queue falls back to Gemini (a non-streaming request has no such guard, and DeepSeek's keep-alive lines keep resetting httpx's read timeout). The whole summary is also capped by `asyncio.timeout(120)`. The summary is cached in Redis (`group_topics:summary:{block_key}`, 24 h) until the block is stored, so a retry after a failed embedding doesn't pay the model again. No `instrument=` (Logfire's global instrumentation applies). At most 5 topics; each message is clipped to 800 characters. **Language**: the prompt asks for the language most of the messages are written in, so topics follow the chat (and the bot, which answers in it), and members' queries meet topics in the same language.
6. **Embed** with `embed_documents` (one batch call, `RETRIEVAL_DOCUMENT`, raises on failure, capped at 60 s) the text `# subject\nsummary`.
7. **Store** (`store_block`), in ONE transaction: insert the topics (`ON CONFLICT DO NOTHING`) and move the cursor to the block's last message. It first takes `FOR SHARE` on that message: if `/clean` deleted it, nothing is stored; if `/clean` runs at the same moment, its DELETE waits for this commit and then deletes these topics too.

## The two wa_llm bugs, avoided

- **Watermark**: `group_topic_cursors` stores the `(timestamp, id)` of the last message of the last stored block, never `now()`. wa_llm set `now()` after a minutes-long run, so messages saved meanwhile were never ingested. The cursor update only moves forward (`WHERE (old) < (new)`).
- **Topic ids**: `uuid5(namespace, f"{block_key}:{n}")`, where `block_key` is sha256 of the block's ordered message ids. wa_llm hashed the LLM's subject, so re-running a block after a crash duplicated its topics. Here topics and cursor commit together, and a re-run hits the same ids.

## Failures

- **Provider unavailable** (`is_unavailable`): HTTP 5xx or `agent/model_chain.py`'s cooldown statuses (401/402/403/404/429: bad key, lapsed billing, mistyped model name, rate limit) from either model (`ModelHTTPError`, OpenAI SDK status errors) or from Gemini embeddings (`ClientError`, `ServerError`); a `ModelAPIError` with no status (connection failure, a model skipped while its cooldown runs, the first-chunk timeout); `httpx.TransportError`; an embedding over 60 s; a lost database connection (`OperationalError`, `InterfaceError`); a `FallbackExceptionGroup` only when every model failed that way. The run stops (the providers are shared, so the other groups would fail too), nothing is counted, and that group goes last next run in case the failure was its own.
- **The same 4xx or timeout in two groups** of one run (`RunFailures`; Gemini answers an invalid API key with a 400, and a provider that streams too slowly times out every summary) is an outage too: the run stops and the first group's count is taken back. With a single group the two can't be told apart.
- **Anything else** (a 400 on this block, output validation exhausted, a summary that hits the 120 s cap, a rejected embedding, a failed store): counted in Redis `group_topics:fail:{group_id}:{block_key}` (7-day TTL). The group waits on that block and the run moves on to the next group; after 3 failed runs the block is skipped (cursor moved past it, no topics) with a warning, so one bad block can't stop a group's topics forever. The run summary logs how many blocks were skipped.
- One group's unexpected error is logged and the run goes on to the next group.

## Search

`agent/tools/search.py` `search_conversation_history`: when the chat is a group (`is_group_jid`) and the setting is on, `search_group_topics` runs first with the run's own `users.id`. The message search runs too, over the whole history, and its hits follow the topics (subject, time range, message count, summary): a summary drops details (a number, a link), and no topic covers messages older than the job's 7-day window, newer than its last run, or in a skipped block. A hit inside a returned topic's time range is kept for the same reason. No topic match returns the messages alone. The tool's signature and docstring did not change. A private chat never takes this branch (nor a `/v1` run: its `web:`/`cli:` or linked private row is never a group, and a key can't be attached to a group row), and `get_group_context` (the opt-in private-to-group bridge) still searches messages only. Same SQL shape as conversation search: inner `ORDER BY embedding::halfvec(3072) <=> …` with `prepare_hnsw_search`, outer threshold (`semantic_similarity_threshold`) and re-sort; limit `semantic_search_limit`.

## Schema

`group_topics` (id, `user_id` → the group's `users.id` with `ON DELETE CASCADE`, `block_key`, subject, summary, `start_at`, `end_at`, `message_count`, `embedding vector(3072)`, `created_at`) with HNSW index `idx_group_topics_embedding_hnsw` on `embedding::halfvec(3072)`, and `group_topic_cursors` (`user_id` PK, `last_message_at`, `last_message_id`, `updated_at`). Both are new tables, so `create_all()` creates them and the index: **no migration file** for them. The stream worker runs `init_db()` at start too (retrying a race with the API, which runs it at the same moment on a fresh deploy), so the tables exist even when the worker starts first. The job's reads use `idx_conversation_messages_user_ts_id` on `conversation_messages (user_id, timestamp, id)`: created by `create_all()` on a fresh DB, and on an existing one by `docs/migrations/2026-11-09-group-topics.sql` (apply it before enabling the job). `/clean` (any level) deletes a chat's topics and cursor with its messages.

## Not done yet

- Save-only group messages are still embedded one by one in `routes/chat.py` `save_message_only`. With topics on, that could stop (fewer embedding calls, faster saves); left for after the pipeline and groups PRs that rewrite that file.
- A daily/weekly summary posted into the group: Devflow `6af21a47be4cc60a82acd731`, to go through the scheduler's paced send lane.
- A message deleted or edited (`/chat/revoke`, `/chat/edit`) after its block was summarised stays in the topic summary; the message search sees the change. A revoke of a block's last message while that block is being summarised stores nothing for it (the same `FOR SHARE` check as `/clean`), and the next run reads the block again without it.
- Sender names are not pseudonymised before the model call (wa_llm does): they already reach the model in every group reply's history.
