# Admin API and runtime settings

Detail behind the admin and runtime-settings gotchas in the root `CLAUDE.md` / `AGENTS.md`. These routes and the `REGISTRY` are the FleetView contract, so also run the contract check described there after changing them.

- **Admin API (`routes/admin.py`, `/admin/*`)** is the management-dashboard contract: `GET/PUT/DELETE /admin/prompt`, `GET /admin/prompt/effective`, `GET /admin/prompt/sections` + `PUT/DELETE /admin/prompt/sections/{key}`, `GET /admin/processes`, `GET/PATCH /admin/settings` + `DELETE /admin/settings/{key}`, read-only `GET /admin/users` and `GET /admin/users/{jid}/messages`, `GET /admin/overview`, `GET /admin/whatsapp/qr`. Separate routers under `/admin` serve broadcasts, bug reports, scheduled sends (`/admin/scheduled-sends`, see `scheduled_sends/CLAUDE.md`) and scheduled tasks (`/admin/scheduled-tasks`, see `scheduled-tasks.md`). It is protected by the standard `X-API-Key` (NOT in `_AUTH_EXEMPT_PREFIXES`)
- **`GET /admin/whatsapp/qr`** proxies the Baileys client's `GET /whatsapp/qr` (link status + pairing QR) with a 5s timeout. It targets Baileys via `get_whatsapp_client_url(None)`, so when `WHATSAPP_CLIENT_URL` is unset in a multi-client deployment (it defaults to `localhost:3001`) or Baileys isn't running, it reports `status="unavailable"` (200, not an error)
- **Runtime settings overlay (`runtime_config.py`)**: a curated subset of settings (TTS/STT, semantic/KB search, history limits, `bot_name`, PDF parser, whitelist, PDF TTL, core-memory length, **`gemini_model`**, **`deepseek_model`**) can be overridden at runtime via the `runtime_settings` table. Code reads them through `runtime_config.get("key")` (env default ← DB override), cached in-process ~10s and busted on write. The `REGISTRY` is the source of truth: `hot=True` means overridable, `hot=False` means display-only/"needs restart" (bootstrap settings: DB/Redis/pool, CORS, rate limits, log level). **Only mark a setting `hot` if its consumption site actually reads via `runtime_config.get()`**, otherwise the override silently never applies. `PATCH /admin/settings` rejects unknown/non-hot keys with 400


## Prompt: what the model gets, and overrides that can't go stale

- **Base prompt = code sections** (`agent/prompt.py` `PROMPT_SECTIONS`: `identity`, `tone`, `tools`, `bursts`, and `operator`, empty in code, for the operator's own instructions), joined by a blank line. An operator override of a section lives in `bot_prompt_overrides` with the sha256 of the code default it was written against (`base_hash`). **It applies only while that default is unchanged**: once a commit changes the section, the code text applies again, the override is kept as `stale` (FleetView shows it, with "re-apply" = `PUT` with the new `default_hash`, or "discard" = `DELETE`), and the process logs a warning once. A code change therefore always reaches the model, which the old whole-prompt `bot_prompt` row could prevent (a saved copy of the default shadowed every later change)
- **Legacy `bot_prompt`**: no longer read. At API startup a row holding text is logged as a warning ("no longer applied"); move what is still wanted to the `operator` section (`PUT /admin/prompt/sections/operator`) or `PUT /admin/prompt`. No migration ships for it (the template has no deployment); a fork with a real row decides its own cleanup
- `PUT /admin/prompt/sections/{key}` takes `{content, base_hash}`: `base_hash` must equal the section's current `default_hash` (409 otherwise: the code changed while the editor was open); content equal to the default deletes the override; `""` leaves the section out. The legacy `PUT /admin/prompt` stores a whole-prompt override (key `all`) under the same rule against the composed default; saving the text the sections give now stores nothing and clears a fresh whole override, while a stale one is kept for re-apply or discard (both compares ignore CRLF and trailing whitespace). A fresh whole override replaces every section: each `GET /admin/prompt/sections` item then has `applied: false` (its `status` still says what is saved) and `sections_overridden` is 0. `is_overridden` and `sections_overridden` come from the same applied set, so an empty section override counts in both. A stored row for a key the code dropped is listed after the sections with `orphan: true` (`status: "stale"`, `applied: false`, empty `default`) and can be removed with `DELETE /admin/prompt/sections/{key}`
- **`GET /admin/prompt/effective?chat=private|group&surface=whatsapp|telegram|web[&user_id=|&jid=]`** calls every hook in `INSTRUCTION_HOOKS` (`agent/core.py`) with a real `RunContext` and joins them like Pydantic AI, so the result is the instructions string a run sends (`tests/mocked/test_effective_prompt.py` compares it with a captured run). Register every instructions function with `@instruction_hook(title)`, never a bare `agent.instructions` (the same test fails). A preview writes nothing (`inject_core_memory` reads only). With `user_id`, or `jid` (any identity column, resolved like the messages route; that chat's platform is used, and a Cloud API user runs as client `cloud` on surface `whatsapp`; both → 422, unknown → 404), it shows that user's core memory to the operator, who can already read their messages through `/admin/users`. The web surface has no sample group chat (422)
- **Per-process settings**: the api and the stream worker (where the chat agent runs) each publish a heartbeat to Redis (`process_heartbeat.py`, `admin:process:<process>:<host>:<pid>`, every 60 s, TTL 180 s) with their start time, a `prompt_code_hash` and the value they use for every REGISTRY setting (secrets masked); a process deletes its key on shutdown, and an older instance of a process is dropped once it has not refreshed for one interval (+15 s), so a replaced container drops out while a concurrent replica stays listed. Malformed heartbeats are skipped. `GET /admin/processes` lists them (`prompt_code_mismatch` when two run different prompt code, e.g. one image rebuilt), and each `/admin/settings` item gets `processes` and `restart_pending` (a restart-only setting the live processes disagree on; the older `started_at` is the stale one). Reads are bounded at 2 s and give `[]` without Redis. The values are the last heartbeat's, so right after a settings PATCH or DELETE a process can show the old value for up to 60 s; secrets are compared masked, so `restart_pending` cannot flag a rotated restart-only secret. `prompt_code_hash` covers `agent/prompt.py`, the hooks' module and the helpers they shape text with (`surfaces.py`, `services/shared_groups.py`), not tool docstrings. The TS clients send no heartbeat
