# services/ — broadcasts, bug reports, cross-platform identity

Loaded on demand when working in this folder. The root `CLAUDE.md` holds the architecture, commands, security model and cross-cutting gotchas. These subsystems span `services/`, `routes/`, `streams/` and the chat clients; read this file before changing any part of them.

## Broadcasts (`/admin/broadcasts`, FleetView-driven)

An operator sends one message (changelog/announcement) to every chat the bot has ever talked to — no recency filter. `routes/broadcasts.py` snapshots recipients into `broadcast_recipients` at creation; the stream worker's third task, `streams/broadcast_consumer.py`, delivers them. Routing/audience decisions are pure functions in `services/broadcast.py`; the pacing math is in `broadcast_pacing.py` (no app imports, so `config.py` can validate with it).
- **Audience** (`private` default | `groups` | `all`) and **platforms** (subset of `baileys|cloud|telegram`; omitted = every client whose `GET /health` answers — URLs have localhost defaults, so "configured" can't be read from settings; an explicitly selected unreachable one is a 400). Opted-out chats are excluded, and the whitelist is checked **per route** against the identity the message actually goes to: a linked user whitelisted only as `tg:…` gets nothing on WhatsApp. A **group must be listed itself**, even under `GROUP_GATING=membership` (which admits it for chat through a member, or on Telegram just by the bot being there) — the bot is mostly silent in those groups, so a broadcast would be unsolicited. The whitelist, opt-out and Cloud window are all re-checked right before each send, so a whitelist removal stops a running broadcast. A whitelist with no entries (`" , "`) counts as no whitelist, as in chat
- **One person, one message**: `_people` groups the audience before routing, so the same WhatsApp human with two `users` rows gets it once — an early `@lid` row whose JID is another row's `whatsapp_lid`, or private rows sharing a phone (`+` stripped). The best row is a phone JID over an `@lid` one, then the newest; if any row opted out, the person is out. Groups and `tg:` rows never merge (`/link` merges are one row already). Extra rows are counted as `skipped_duplicate` in the preview and never snapshotted
- **Routing columns on `users`**, all set by `_record_client` on every `/chat/enqueue` (only changed columns are written): `last_client_id` (platform last used — tried first for a `/link`-merged user), `whatsapp_client_id` (Baileys vs Cloud, which the JID can't tell; NULL = Baileys), `cloud_last_inbound_at` (bumped on every Cloud message). **Cloud only reaches chats whose `cloud_last_inbound_at` is < 23h old** (free-form outside Meta's 24h window needs a template, not implemented) — others are `skipped`/`cloud_window`, re-checked at send time. Legacy rows have NULLs: a NULL `whatsapp_client_id` means Baileys only when no Cloud client is deployed; with one the private row is ambiguous (maybe a Cloud-only user who never saw the Baileys number — a spam-report risk) and is `skipped`/`unknown_client` until the user writes again (`skipped_unknown_client` in the preview). "Deployed" is the `/health` probe **OR** `cloud_seen(db)` (any row with `whatsapp_client_id = 'cloud'`), so a Cloud client that is slow or restarting during one probe can't get its users queued for the Baileys number; the Baileys lane re-checks it (and a user who has since written through Cloud) at send time. A **WhatsApp group is never ambiguous**: the Cloud API has no groups, and a group where the bot is never mentioned keeps a NULL client forever. Legacy Cloud chats also have no `cloud_last_inbound_at`, so they're window-skipped too
- **Opt-out, opted in by default**: `users.broadcast_opt_out` (on `users`, not preferences, so `/clean all` never re-subscribes). Three ways: the footer (`broadcast_footer`, snapshotted per broadcast), `/broadcast on|off` (NOT in `ADMIN_ONLY_COMMANDS`: any member may read a group's state with a bare `/broadcast`, the handler requires `is_group_admin is True` for `on`/`off`, and group replies say "This group…"), and the `set_broadcast_subscription` agent tool ("stop sending me updates"). `/link` and `/linkphone` merges OR the two rows' flags; after `/unlink` the new Telegram chat starts opted in (accepted). In a group only an admin may change it: the tool (like every group-changing tool, via `agent/tools/_group.py` `group_admin_refusal`) detects a group by `is_group_jid(deps.whatsapp_jid)` and requires `AgentDeps.is_group_admin is True`, threaded `ChatRequest` → stream job field → `process_chat_job_direct` → `AgentDeps`. Both clients resolve admin status for **every addressed group text message**, bounded at 3s (`ADMIN_LOOKUP_TIMEOUT_MS`; a timeout = not admin): Baileys a live `groupMetadata` for slash commands and the 5-min `group-cache.ts` entry otherwise (safe for `clean_user_data` too, because `group-participants.update` evicts the group on promote/demote — including a fetch already in flight, which later callers no longer join); Telegram `getChatMember`, except that a message whose `sender_chat` is the group itself is an **anonymous admin** (posting as the group is an admin-only right; `from` is then the fake @GroupAnonymousBot) and counts as admin with no API call. Baileys voice notes are transcribed first and take the text path, so they get admin status; Telegram voice, and photo/document captions on both, don't (fails closed)
- **At most one active broadcast, enforced in the DB**: create and resume take `pg_advisory_xact_lock(BROADCAST_LOCK_KEY)` around "is one queued/running?" + the write (the health probe runs first, outside the lock). Every status change — API and worker — is a conditional `UPDATE … WHERE status = …`, so a cancel is never overwritten by the worker completing/pausing it, and a lost race answers 409. Verified against real Postgres (4 concurrent creates → 1 active; without the lock → 4)
- **A send that may have been delivered is never retried**: each recipient is claimed first (`_claim`: `attempt_started_at` set and committed with a conditional `UPDATE … WHERE status='pending' AND attempt_started_at IS NULL`; 8 concurrent claims on real Postgres → 1 winner) and every recorded outcome clears it. Lanes only pick unclaimed rows; "done?" counts claimed ones too (`_has_pending`). A claim older than `ORPHAN_AFTER` (5 min) — a worker crash, a lane cancelled mid-send, a "sent" write that failed 3 times — is swept each tick to `failed`/`unknown`, never re-sent. `classify_outcome` decides the rest: **release** (503, nothing sent: claim dropped, stays pending), **final** (400/403/404/422, per-recipient, not a breaker failure), **unknown** (5xx, no status, read/write timeouts and errors, a dropped connection, a non-JSON body, `success: false` — failed for good, counts for the breaker), **retry** (other 4xx such as 401/429, and connect/pool errors that prove no connection — up to 3 attempts)
- **Chat-client status contract** (what makes the classification honest): Baileys `send-text` 500 = `sendMessage` threw, maybe after delivering → unknown. Cloud (`utils/send-error.ts`, `GraphApiError`): Graph 429 → 429, other Graph 4xx → 422 (dead number, closed 24h window — nothing sent), timeout/Graph 5xx/anything else → 502; the error text is generic because the Graph body can contain the phone number. Telegram (`utils/chat-id.ts` `sendErrorResponse`): invalid id 400, `GrammyError` 403 → 403, 429 → 429, other 4xx → 422, 5xx and `HttpError` (network, timeout, unparsable) → 502
- **One sender fleet-wide**: a Redis lease (`broadcast:lock`, 300s TTL, heartbeat 20s, compare-and-extend Lua). Lanes share a `_Lease` with the heartbeat, stamped with the time each successful renewal was *sent*; a lane starts a send only while `remaining() >= SEND_BUDGET_SECONDS` (130s — one worst-case send: Telegram's 120s lane timeout, or Baileys typing + ≤8s + send-text at 30s each), and the heartbeat gives up at `TTL - SEND_BUDGET` (170s) without a renewal, so everything sent lands before another worker could take the lease. Each renewal is bounded at `RENEW_TIMEOUT_SECONDS` (10s; the worker's shared Redis client has no socket timeout, because the stream consumers block in `XREADGROUP`, so a half-open connection would otherwise hang it). The Telegram lane has its own 120s HTTP client: the client's auto-retry can hold a send for ~2 min (429 waits ≤30s ×3, 5xx backoff), and a shorter timeout would record as unknown a send that still lands
- **Supervisor + lanes**: `run_broadcast` ticks every 15s — sweeps orphaned claims, (re)starts a lane for each platform with unclaimed pending recipients (covers a lane that exited during a pause/resume, and a crashed lane, which waits one tick). A DB error in a tick is logged and retried next tick; it never tears the lanes down. When the broadcast stops running, the lease is lost or the supervisor itself fails, it does **not** cancel lanes: it sets a shared `stop` event (checked between messages, wakes any sleep) and waits up to `LANE_DRAIN_SECONDS` (150s, longer than one worst-case send) for in-flight sends to finish and be recorded; only a lane still running after that, or a worker shutdown, is cancelled (its claim is swept to `unknown`). **Pauses are broadcast-wide**: any circuit-breaker trip or a disconnected client stops every lane. The 30-min disconnect clock is module-level per (broadcast, platform), so lane restarts and pause/resume don't reset it
- **Baileys anti-ban pacing** (hot `broadcast_*` settings, validated at boot by `config.py` and on PATCH, with upper bounds from `broadcast_pacing.SETTING_MAXIMA`; a `DELETE /admin/settings/broadcast_{min,max}_delay_seconds` that would leave min > max is a 400): jittered 20-60s gap, "typing…" (`POST /whatsapp/typing`, 2-8s by length) before each message, a 600s ±30% pause every 15, a rolling 24h cap of 150 **across broadcasts** (counted from `sent_at`), a 09:00-21:00 window in `broadcast_timezone` (DST-correct: waits are computed in UTC), sends to the stored full JID (no `onWhatsApp` lookup burst). A starting lane rebuilds its place in the schedule from recent `sent_at` values (`resume_pacing`), so resumes, lease handovers and worker restarts never skip a gap or batch pause. 5 consecutive unknown/retry failures on ANY lane pause it (`consecutive_failures`) — on Baileys a failure spike is often the start of a restriction; on the fast lanes a wrong API key (401) would otherwise fail the whole audience in seconds. 30 min of 503s pause it (`client_disconnected`). Telegram (50ms) and Cloud (200ms) lanes are fast. 1000 users at the defaults ≈ a week; `POST /preview` returns `estimated_baileys_seconds`
- **Outcomes** (`error_code`): `not_on_whatsapp` (404), `blocked` (Telegram 403 — blocked, deactivated or removed from the group. Deliberately **no** automatic opt-out: the row may be a linked user still on WhatsApp, or a group that re-adds the bot), `invalid_address` (400), `rejected` (422), `unknown` (may have been delivered), `http_<n>`/`transport_error` (retried to 3 attempts), `opted_out`/`user_deleted`/`cloud_window`/`unknown_client`/`not_whitelisted` (skipped). A sent message is saved as an `assistant` row in that chat's history so a reply like "what's this?" has context. Text is capped at 3500 chars so text + footer (≤500) fits one Telegram message
- **FleetView contract**: `BroadcastStatus` (`queued|running|paused|completed|cancelled`), `BroadcastRecipientStatus` (`pending|sent|failed|skipped`), `BroadcastAudience`, `BroadcastPlatform` in `schemas.py` are closed enums once FleetView mirrors them. `idempotency_key` makes a timed-out create safe to retry (replay answers 200 with the original; reusing a key with a different text, audience or explicit platform set is a 422; omitted platforms match any). `GET /admin/broadcasts/{id}` is rate-limit exempt for polling; the list counts all rows in one grouped query; recipients page by limit/offset over row id — the order is stable, but with a `status` filter rows move in and out of the set while sending, so a page can skip or repeat a row. `pause`/`resume`/`cancel` run `_transition` in the threadpool: resume waits on the advisory lock, which a create holds for its whole snapshot

## Bug reports (`/admin/bug-reports`, FleetView-driven)

Reports land in the `bug_reports` table (`services/bug_reports.py`) and are triaged through `routes/bug_reports.py`. On/off with `BUG_REPORTS_ENABLED` (default `true`, hot via `/admin`): it hides the tool (`prepare` hook), its prompt section (`bug_report_guidance` in `agent/core.py`, an instructions hook so it survives a `bot_prompt` override) and the automatic capture.
- **Agent-filed** (`report_bug`, `agent/tools/bug_report.py`): when the user asks (`source=user`, category `user_request`) or on the agent's own judgement (`source=agent`: `user_complaint`, `wrong_answer`, `tool_failure`, `other`). Identity comes from `AgentDeps` (incl. `job_id`), never from arguments. Any group member may file one; abuse is capped at `BUG_REPORTS_PER_USER_PER_HOUR` (default 5, per chat row, counted from `created_at`; `/admin` rejects values < 1 so an emptied FleetView box can't silently stop reports — `BUG_REPORTS_ENABLED` is the off switch)
- **Automatic** (`record_auto_report`: never raises, opens its OWN session because the caller's may be in a failed transaction, and blocks on the DB, so callers run it with `asyncio.to_thread` AFTER the user-facing steps — the ❌/fallback reply and the job status): `model_error` (the `MODEL_ERRORS` fallback in `streams/processor.py`), `job_crash` (its generic `except`), `pdf_failure` (`pdf_consumer`: only once retries are exhausted or the error is non-retriable, plus a document that ends `partial`)
- **Dedup**: `fingerprint` = sha256(source, error type, location). The error type includes an HTTP `status_code` and, for an exception group, its sorted members. The location is the innermost `ai_api` frame as `file:function` (no line numbers, so a deploy doesn't split a bug); a PDF has no useful traceback and passes `"<why>|<normalize_message(reason)>"` instead (ids, paths, numbers stripped), because one `ValueError` covers many unrelated parse failures. Writes are one `INSERT … ON CONFLICT (fingerprint) WHERE status = 'open' DO UPDATE` against the partial unique index `uq_bug_reports_open_fingerprint`, so concurrent identical failures bump one row (8 concurrent writers on real Postgres → 1 row). A bump increments `occurrences` and replaces the whole **sample** (`user_id`, `whatsapp_jid`, `client_id`, `conversation_type`, `job_id`, `document_id`, `models`, `error_detail`, `context`) with the latest occurrence, so a row never shows one user's chat next to another's job; `created_at` stays "first seen". A resolved or ignored report never absorbs a repeat (a regression is a new row), and reopening one while another open report has its fingerprint is a 409
- **Context and privacy**: every report copies the chat's last 10 messages (≤1000 chars each) into `context` (JSONB, `none_as_null=True`). `scrub_user_reports` removes everything a report copied from a chat — `context` and `error_detail` (a DB error can quote the user's text) to SQL NULL, `description` to `""`, and a `user`/`agent` title (agent-written) to `(removed by /clean)`. It runs inside `/clean` (any level, so also the `clean_user_data` tool) and inside `/link` / `/linkphone` merges for the discarded Telegram orphan, before its row is deleted (otherwise its reports would sit under `user_id` NULL, out of `/clean`'s reach). What remains is metadata: source, category, status, error type, models, counts, timestamps and the chat id (the `users` row keeps that too). **User-row lock**: the scrub and both writers (`record_auto_report`, `file_report`) take `SELECT … FOR UPDATE` on the `users` row before touching messages, so a report can't snapshot messages a concurrent `/clean` is deleting; a writer whose user row is gone stores `user_id`/`context` NULL
- **Routes**: `GET /admin/bug-reports` (`status`, `source`, `limit` ≤200, `offset`; ordered by `last_seen_at desc`; summaries + `counts_by_status`, which applies the same `source` filter as `total`), `GET /{id}` (adds description, context, error_detail, models; rate-limit exempt), `PATCH /{id}` `{status, resolution_note?}` (`resolved_at` set on resolve and kept if already resolved, cleared otherwise; an omitted note is unchanged, `null` clears it; 409 as above), `DELETE /{id}`. `GET /admin/overview` gained `open_bug_reports`
- **FleetView contract**: `BugReportSource` (`user|agent|model_error|job_crash|pdf_failure`) and `BugReportStatus` (`open|resolved|ignored`) in `schemas.py` are closed enums; `category` and `error_type` are open strings. The FleetView page is not built yet (planned: a per-bot tab like Broadcasts, the open count on the Fleet card, a 404 = "unsupported")
- New table only, so `create_all()` creates it and its partial index; no migration SQL

## Cross-platform identity (`/link`, phone auto-link)

One human on WhatsApp and Telegram can share one `users` row (history, core memory, preferences). Two ways, both in `services/`, both with the **discard-orphan** policy (the Telegram orphan row is deleted; `cascade="all, delete-orphan"` drops its messages, preferences and core memory; the WhatsApp row is kept and gains `telegram_jid`):

- **`/link` codes** (`services/link.py`): `/link` mints a 6-digit code in Redis (10 min TTL) on one platform, `/link <code>` on the other merges. Handled in `routes/chat.py` before `parse_and_execute` (needs async Redis)
- **Phone auto-link** (`services/autolink.py`, `POST /chat/link-phone`, `LinkPhoneRequest`): on Telegram, `/linkphone` (client-side, `handlers/link-prompt.ts`) shows a `request_contact` keyboard; the `message:contact` handler forwards the phone, `contact.user_id` and `ctx.from.id` verbatim (the client decides nothing). `try_autolink` refuses unless ALL hold: the caller is not a group; it is an unlinked `tg:` orphan; the contact carries a `user_id` equal to the sender's (anti-hijack — a shared card for someone else carries THEIR id); the phone normalizes to a plausible international number (`+` and 8-15 digits, or 12-15 bare digits — a bare 11-digit number could be a national mobile misread as `+1…`, so NANP users need the `+` or `/link`); exactly one private, non-Telegram row has that phone; and that row is not already linked. The route rejects group JIDs before touching the DB (under `GROUP_GATING=membership` `_is_whitelisted` admits groups)
- **Identity columns**: `users.whatsapp_jid` is `UNIQUE NOT NULL` and holds `tg:<chat_id>` for an unlinked Telegram user; `telegram_jid` is set only by a merge. `get_or_create_user` looks up `telegram_jid` first for a `tg:` JID and **skips the LID/phone merge steps for Telegram** — letting a `tg:` JID reach the phone merge would let it silently take over a WhatsApp row. That is why phone linking is a separate, refusing-by-default path
