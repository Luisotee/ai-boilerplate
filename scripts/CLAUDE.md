# scripts/ — several bots on one host

Loaded on demand when working in this folder. The root `CLAUDE.md` holds the architecture, commands, security model and cross-cutting gotchas. Also read this before changing `setup.sh`, `upload-kb.sh` or the port/name/volume parts of `docker-compose.yml`.


Forks of this repo share a VPS, so everything host-global must be unique per checkout. `scripts/instance_check.py` (stdlib Python, no repo imports — a fork copies the one file **unchanged**) does the checking; `setup.sh` is a thin caller. It reads the port variables, their defaults and the default `SERVICE_NAME` from the checkout's own compose file (`specs_from_compose`: every `${X_PORT:-N}:<container port>` and `${SERVICE_NAME:-name}`), so a fork with other services or port defaults needs no edit. There is no built-in fallback: without a compose file `fix` / `assign-ports` refuse (exit 2) rather than guess ports that may not exist. It is covered by `packages/ai-api/tests/unit/test_instance_check.py` (commands run against a `Host` built from data via the `load_host` seam, so no Docker is needed) and linted/formatted with the ai-api ruff config (`pnpm lint` / `pnpm format` include `scripts/`).
- **What is host-global, and what scopes it**: container names, the network and the `…-api` image tag follow `SERVICE_NAME`; the eight published ports follow the `*_PORT` vars; the six volumes and the three TS client images follow the **Compose project name**, which is the directory basename unless `COMPOSE_PROJECT_NAME` is set. Those are two independent namespaces
- **Ports are checked against three sources**, because a listening-socket probe alone misses a stopped stack and a profile (`telegram`, `cloud`, `dev`, `whisper`) that was never started: containers Docker knows (`docker inspect` `HostConfig.PortBindings`, running or not), ports *declared* by other compose projects (`docker compose --profile '*' config --format json`, run in that project's directory with a scrubbed environment so our exported vars can't override its `.env`; the output holds that project's secrets and is parsed for ports only), and live sockets. "Other projects" = working dirs of foreign containers + `../*/` with a compose file + `SIBLING_DIRS` (colon-separated) for a stopped stack that lives elsewhere. Ours vs theirs is decided by the `com.docker.compose.project.working_dir` label, never by name
- **`./setup.sh --check`** (also printed when you keep an existing `.env`). Exit codes: 0 clean; 1 collisions (the check may also be incomplete — see its notes); 2 incomplete with nothing found (Docker unavailable, or a sibling's compose file would not render); 64 usage error; `setup.sh` itself exits 69 without `python3`. With Docker unavailable, a port that is merely in use is listed as "possibly this checkout's own stack", not as a collision, and `--fix` is not suggested (it would refuse). **Pending port changes**: when this checkout's own container for a service publishes a different host port than `.env` now configures (`port_services` maps each `*_PORT` to its service), it says so — the next `up` would silently move that port. A neighbour that was cloned but never configured (no `.env`) still renders, via `config --no-env-resolution`
- **`./setup.sh --fix`** writes exactly: the clashing ports (moved), every `*_PORT` that was an implicit default (pinned), and `DATABASE_URL` / a `*_CLIENT_URL` that still has the stock `localhost:<old port>` shape (a missing `*_CLIENT_URL` is added). Nothing else. The backup `.env.bak.<timestamp>` is a byte copy, created mode 600 with `O_EXCL` (gitignored with the `.env.tmp*` temp files). The rewrite keeps CRLF, `export` prefixes, quote style, an inline comment, a symlinked `.env`, the file's mode (and owner, when run as root) and non-UTF-8 bytes. When `POSTGRES_PORT` moves and `.env` has no active `DATABASE_URL`, it says local dev must follow by hand. It **refuses when Docker state is unavailable** (exit 2): our own running stack would look like any other listener and be "fixed" away. A port that our container AND another project's both publish is moved — the other project's claim always wins over "it's ours". A moved port applies at the next `docker compose up -d`, and external targets (proxy, webhook URL, FleetView base URL) must follow
- **`.env` is read with Compose's dotenv rules** (`parse_env`: optional `export`, quotes, inline ` #` comments, last assignment wins); `setup.sh` reads values through `instance_check.py get` and writes through `set`, which quotes a value containing ` #` or `$` (Compose interpolates unquoted ones). `upload-kb.sh` repeats the same rules in bash (`env_get`) for `AI_API_KEY`, `AI_API_PORT` and `AI_API_BIND`, and targets the bind address instead of `localhost` when it is one specific address
- **A moved or renamed checkout**: containers of our project whose recorded `working_dir` no longer exists are counted as ours (and noted). Volumes/networks of our project with no containers at all (a plain `docker compose down`) are assumed ours on an existing `.env`
- **`SERVICE_NAME` must be lowercase words joined by single `-`/`_`** (`check-name` and `setup.sh` use the same regex; `bot_` or `a__b` would make an invalid image tag) **and is refused when another project already owns** a `<name>-<service>` container, or `<name>-network` when the compose file names the network after `SERVICE_NAME` (the boilerplate does; the forks keep a project-scoped network, so the check is off there). An `…-api:latest` image built by another project is only a warning (the label records the last builder). `setup.sh` treats only an `ERROR` line as "taken", so a crashing helper can't reject every name
- **The Compose project name is never changed on an existing deployment** — that switches the stack to new, empty volumes (database, WhatsApp session, uploads). When another checkout uses the same name (same-named directories: shared volumes, and `up`/`down` in one replaces the other's containers), a *first* setup with no containers of its own offers `COMPOSE_PROJECT_NAME=<SERVICE_NAME>`; every other case only warns. For the same reason the compose file has no top-level `name:` and no explicit volume names
- **`*_BIND`** (`AI_API_BIND`, `WHATSAPP_API_BIND`, `WHATSAPP_CLOUD_BIND`, `TELEGRAM_BIND`): host address an app port is published on — an address only, no trailing `:`. The default must stay **empty**, not `0.0.0.0`: `'${X_BIND:-}:${X_PORT}:…'` with an empty IP renders exactly like the old two-part form (all interfaces, IPv4 and IPv6), while `0.0.0.0` would drop IPv6. The empty-IP form is Compose implementation behaviour rather than documented syntax; it is verified by comparing `docker compose config` output
- **Re-running `./setup.sh` over an existing `.env` reconfigures, it doesn't reset**: the old file is backed up first (`instance_check.py backup`), then `carry` copies every non-empty line of it into the fresh template **verbatim** (quotes and `$` stay as written; keys the template lacks are appended under `# Kept from the previous .env`). Only `DATABASE_URL` is skipped and rebuilt. The secret prompts default to the current value ("Enter to keep the current one") — a new Postgres password would lock api/worker out of the existing volume — and a kept value's line is not rewritten
- `upload-kb.sh` targets `http://localhost:<AI_API_PORT from .env>` unless `AI_API_URL` is exported. It does not read `AI_API_URL` from `.env` — that is the local-dev URL, pinned to `:8000`
